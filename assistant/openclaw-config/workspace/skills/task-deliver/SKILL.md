# Task Deliver（任务产物与交付物规范）

让每个任务都有"可验证交付物"，并让交付回传在微信上清晰可读。借鉴 WorkBuddy 的任务目录机制。

## 任务目录约定

每次接到需要产出文件的长期任务时：

```bash
TASK_DIR="$HOME/tasks/$(date +%F)-<任务短名>"
mkdir -p "$TASK_DIR"
```

- 目录名格式：`YYYY-MM-DD-任务短名`（如 `2026-08-17-workbuddy-benchmark`）。
- 任务产物一律放 `$TASK_DIR`，不要散落 `/tmp`。
- 若任务是多轮迭代（当天或跨天续做同一主题），**复用同一任务目录**，在目录内建 `history/` 存放历史版本，主交付物放根目录。

## 交付物清单（DoD）

任务完成时，向用户交付以下内容（微信友好格式，不用表格）：

```
✅ 完成：<任务一句话结论>
📁 产物目录：~/tasks/<日期>-<任务名>/
📄 交付物：
  1. <文件名> — <一句话说明>（<大小/页数>）
  2. <文件名> — ...
🔄 可续跑：直接说"继续"即可基于该目录续做
```

- 微信发完清单后，若用户在微信里点开不了文件，补充说明文件在电脑上的完整路径。
- 涉及生成图表的任务，把图表 `.png` 路径也列入交付物。

## 续跑规则

- 用户说"继续 / 接着上次 / 在之前基础上"时，先 `ls ~/tasks | tail` 找到最近任务目录，读取其中已有交付物与 `history/`，再继续。
- 新版本产物命名加版本后缀（`_v2`、`_v3`），不覆盖旧版。
- 每次续跑完成后，往 `$TASK_DIR/history/` 追加一条 `changelog.md` 记录本次改动。

## 清理

- 任务目录保留最近 30 天；更早的可询问用户后 `trash`（用 `trash` 不用 `rm`）。
- 避免把任务目录建在 `~/.openclaw` 内部。

## 关联

- 交付物需要 docx/pptx → 使用 `office-docs` skill。
- 交付物需要研究报告 → 使用 `deep-research` skill。
- 交付物需要图表 → 使用 `data-analysis` skill。
